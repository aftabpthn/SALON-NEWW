# OBSERVABILITY.md — Observability Standards

> **Primary AI Role:** Cloud Architect
> **Status:** Living document. Operational detail: `docs/monitoring.md` (alerts), `docs/logging.md` (logs).

## 1. Purpose

How we see inside AuraShine in production: logs, metrics, health, tracing by
correlation id, and the business signals that matter to a salon SaaS.

## 2. The Three Signals

1. **Logs** — structured JSON (level, timestamp, `requestId`, `tenantId`, route, duration). Redaction list enforced by the logger (docs/logging.md). One error log per failure, at the handling layer.
2. **Metrics** — request rate/latency/error-rate per route group; worker queue depth and job outcomes; WebSocket connection counts; PostgreSQL connection pool, long-query count, and backup age; per-tenant usage events (SaaS metering).
3. **Health** — `GET /api/health` (liveness + dependency summary); `npm run check:server` for scripted checks; WebSocket connectivity probe.

## 3. Correlation

- Every request gets a `requestId` at the edge; it propagates into service logs, audit rows, queued jobs and outbound webhook deliveries spawned by that request.
- A support ticket with a `requestId` (surfaced in 500 responses) must let an engineer reconstruct the full path from logs alone.

## 4. Business Observability

Salon SaaS dies quietly when tenants stop transacting — watch business signals, not just servers:

- Invoices/day per tenant vs trailing average (billing stopped = incident-grade signal).
- Message delivery failure rates per channel (WhatsApp/SMS/email).
- Booking funnel health (widget requests vs confirmations).
- Backup age, scheduler last-run timestamps, snapshot job freshness.
- KPI monitors and tenant-health views surface in the super admin console.

## 5. Dashboards & Alerts

- Dashboards per audience: platform ops (infra + API), super admin (tenant health), on-call (alert overview).
- Every alert: owner + runbook link + severity (page vs ticket) — rules in `docs/monitoring.md`. No runbook, no alert.
- Weekly alert review prunes noise; an alert that always gets ignored gets fixed or deleted (with approval).

## 6. Retention

- Logs: rotated, bounded disk usage, retention per docs/logging.md.
- Metrics/snapshots: platform analytics snapshots persisted (`platform_analytics_snapshots`) for trend history.
- Audit rows: retention per docs/audit-log.md (compliance-driven, longer than logs).

## 7. AI Instructions

- New feature = new signal check: does it need a metric, a log field, or nothing? Say which in the PR.
- Never add chatty per-row logging inside loops or transactions.
- Never log the fields on the redaction list, even at debug level.

## 8. Acceptance Criteria

- A dead API, stuck worker, failed backup or silent tenant is detectable within 5 minutes from dashboards/alerts.
- Any production error is traceable end-to-end by `requestId`.
- Log volume stays bounded under load.

## 9. Future Roadmap

- OpenTelemetry-compatible export once external tooling is chosen.
- Per-tenant SLO reporting in the super admin console.

## 10. Data Migration Signals

`GET /api/settings/integrations/import-monitoring` is the tenant/branch-scoped migration signal source. Alert thresholds, owners, safe recovery steps, AI degradation behavior, and release checks are defined in `docs/DATA_MIGRATION_RUNBOOK.md`.

## 11. What ships today: the `/metrics` endpoint

Sections 2 and 5 describe the target state. This section documents what is
actually implemented and scrapeable right now.

### Endpoint

`GET /metrics` — Prometheus text exposition format, mounted **outside**
`/api/v1` so scrapers need no tenant context.

Access is guarded by its own bearer token, because the series expose route
latency and failure rates across every salon on the platform:

```
curl -H "Authorization: Bearer $METRICS_AUTH_TOKEN" https://<host>/metrics
```

`METRICS_AUTH_TOKEN` is generated by Terraform into the runtime secret. If it is
unset, the endpoint returns **404 outside local development** rather than
publishing platform-wide operational data unauthenticated.

### Series

| Metric | Type | Labels |
| --- | --- | --- |
| `aurashine_http_requests_total` | counter | `method`, `route`, `status` |
| `aurashine_http_request_duration_seconds` | histogram | `method`, `route` |
| `aurashine_http_errors_total` | counter | `route`, `status` (5xx and 429) |
| `aurashine_tenant_slow_requests_total` | counter | `tenant`, `route` |
| `aurashine_worker_cycles_total` | counter | `worker`, `outcome` |
| `aurashine_worker_run_duration_seconds` | histogram | `worker` |
| `aurashine_worker_step_failures_total` | counter | `worker`, `step` |
| `aurashine_db_pool_connections` | gauge | `state` (idle/in_use/total) |
| `aurashine_metrics_series_dropped_total` | counter | — |
| `aurashine_build_info` | gauge | `version`, `environment` |

`worker.outcome` is one of `ran`, `skipped` (another replica holds the lease),
`contended` (the outgoing leader's cycle is still running), or `unavailable`.

### Cardinality

Two deliberate constraints, because cardinality is what kills self-hosted
Prometheus:

1. **`tenant` appears on one family only** — the slow-request counter. Putting a
   tenant label on every series would multiply each one by the customer count;
   here the series count is bounded by how many salons are actually having a bad
   time. This is the metric that answers "which salon is slow?".
2. **Every family caps its distinct label sets** (10,000). Overflow increments
   `aurashine_metrics_series_dropped_total` instead of growing without bound. A
   non-zero value there means a label is leaking identifiers — investigate it.

`route` is a normalised label, not the raw URI: query strings are stripped and
identifier-shaped segments collapse to `:id`
(`/api/v1/clients/3f25…/notes` → `/api/v1/clients/:id/notes`).

### Error reporting

5xx responses are logged with route, status, elapsed time and tenant, and — when
`ERROR_WEBHOOK_URL` is set — forwarded to that endpoint as JSON (Sentry, Slack,
or any JSON sink). Forwarding is rate-limited globally (60/minute) and
per-route (one report per minute, with suppressed repeats counted into the next
report), so an outage cannot turn into thousands of outbound requests.
